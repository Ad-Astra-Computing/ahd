Design eval, not design theater

A framework for refusing generated sameness.

AHD treats design output as something to inspect, lint, stress, and critique before it gets mistaken for taste. It is for designers, engineers, and founders who have already seen the pattern and want a way to measure it.

The point is not another prompt ritual. The point is a repeatable editorial standard, an eval harness that makes the failure modes visible, and a manifest that says plainly what works now and what depends on external infrastructure.

eval-live.sh
ahd eval-live swiss-editorial --brief briefs/landing.yml --models <specs> --n 10

What ships

These are in the box today. They define the current working surface of AHD without hand-waving.

  • brief compilerturns a design brief into structured evaluation input
  • 28-rule linterflags recurring patterns associated with generic output
  • eval harnessruns controlled comparisons across model specs and samples
  • vision-critic scaffoldbase structure for image-aware critique workflows
  • MCP serverconnects the tooling surface to editor and agent workflows
  • editor pluginsintegrations for working where design and code already happen
  • eight tokensinitial token set for visual and editorial constraints

What is gated

These are intentionally separated because they depend on third-party access, packaging work, or broader distribution.

  • live frontier-model callsneeds API keys
  • live vision critiqueneeds multimodal key + screenshot pipeline
  • standalone npm packages for the editor pluginspackaging and release pipeline pending
  • additional tokensexpands after the first set proves durable

AHD is opinionated on purpose. It assumes generated work should survive contact with editorial standards, not just look plausible for twenty seconds. If that premise already makes sense to you, the repository is the product surface.

Read the code, run the eval, inspect the failures, and decide whether the output earns its keep.
