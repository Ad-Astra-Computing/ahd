        <div class="hero-copy">
          <div class="eyebrow">A framework for people who can already see the problem</div>
          <h1 id="headline">Less generated surface. More accountable taste.</h1>
          <p class="lede">
            AHD is not another prompt wrapper for landing-page mush. It is a working evaluation stack for teams that want a brief to survive contact with models, tools, and defaults. If the page still looks inevitable after ten generations, the system failed. <strong>AHD makes that failure inspectable.</strong>
          </p>
        </div>

        <div class="sidebar">
          <aside class="note" aria-labelledby="why-ahd">
            <h2 id="why-ahd">Why it exists</h2>
            <p>
              Designers, engineers, and founders do not need another lecture about slop. They need a repeatable way to define a standard, lint against it, run live evals, and separate what is finished from what still depends on external infrastructure.
            </p>
          </aside>

          <section class="terminal" aria-labelledby="run-eval">
            <div class="terminal-head">
              <span id="run-eval">Run the eval</span>
              <span>bash</span>
            </div>
            <pre><code class="language-bash">ahd eval-live swiss-editorial --brief briefs/landing.yml --models &lt;specs&gt; --n 10</code></pre>
          </section>
        </div>
      </section>

      <section class="grid" aria-label="Manifest">
        <section class="manifest" aria-labelledby="what-ships">
          <h2 id="what-ships">What ships</h2>
          <p>The core system is usable now. These parts are in scope and intended to be read, inspected, and extended.</p>
          <ul>
            <li><span class="index">01</span><span class="item">brief compiler</span></li>
            <li><span class="index">02</span><span class="item">28-rule linter</span></li>
            <li><span class="index">03</span><span class="item">eval harness</span></li>
            <li><span class="index">04</span><span class="item">vision-critic scaffold</span></li>
            <li><span class="index">05</span><span class="item">MCP server</span></li>
            <li><span class="index">06</span><span class="item">editor plugins</span></li>
            <li><span class="index">07</span><span class="item">eight tokens</span></li>
          </ul>
        </section>

        <section class="manifest" aria-labelledby="what-gated">
          <h2 id="what-gated">What is gated</h2>
          <p>These pieces are intentionally marked as dependent on external access or packaging work, rather than implied as complete.</p>
          <ul>
            <li><span class="index">A</span><span class="item">live frontier-model calls (needs API keys)</span></li>
            <li><span class="index">B</span><span class="item">live vision critique (needs multimodal key + screenshot pipeline)</span></li>
            <li><span class="index">C</span><span class="item">standalone npm packages for the editor plugins</span></li>
            <li><span class="index">D</span><span class="item">additional tokens</span></li>
          </ul>
        </section>
      </section>

      <section class="splitline" aria-labelledby="closing-statement">
        <p class="statement" id="closing-statement">
          If the standard matters, the method cannot hide behind vibes. AHD turns aesthetic judgment into a visible, testable process without pretending taste can be automated away.
        </p>
        <p class="smallprint">
          The point is not to generate more pages. The point is to force specificity: what the brief requires, what the linter rejects, what the eval records, and which dependencies are still outside the repo. The code is the argument.
        </p>
